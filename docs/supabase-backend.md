# Dayflow Supabase Backend

This backend keeps the frontend contract simple while enforcing role boundaries in Postgres with RLS. The client should use the normal Supabase browser SDK; sensitive role and payroll permissions are not trusted to frontend code.

## Apply the schema

Run the migration in `supabase/migrations/001_initial_schema.sql` using the Supabase SQL editor, or with the Supabase CLI:

```bash
supabase init
supabase db push
```

## Auth and profile creation

Use Supabase Auth for passwords and email verification. The custom `public.users` profile row is linked to `auth.users.id`.

Recommended signup call:

```ts
await supabase.auth.signUp({
  email,
  password,
  options: {
    data: {
      employee_id: employeeId,
      name,
    },
  },
});
```

The database trigger `public.handle_new_auth_user()` creates the `public.users` row automatically. Self-signup always creates an `employee` account, even if a client sends `role: 'admin'`.

This is better than doing a separate browser insert into `public.users`, because email verification can mean the user does not have an authenticated session immediately after signup.

Why: letting browser clients choose `admin` during signup is a direct privilege escalation. For the demo, create the first admin with the SQL editor or service role after that user signs up:

```sql
update public.users
set role = 'admin'
where email = 'hr@example.com';
```

After that, an admin can edit other users through the app.

## Table model

`public.users`

- One row per Supabase Auth user.
- Stores HRMS fields: `employee_id`, `role`, `name`, `phone`, `address`, `job_title`, `department`, `salary`, `profile_pic`.
- Employees can read their full own profile but update only `phone`, `address`, and `profile_pic`.
- Admins can read and update all user profiles.

`public.attendance`

- One row per user per date, enforced by `unique (user_id, date)`.
- Employees can insert their own check-in row and update only `check_out_time`.
- Admins can read, edit, and delete all attendance rows.

`public.leave_requests`

- Stores employee leave applications and admin decisions.
- Employees can insert their own pending requests and read their own requests.
- Admins can read all requests and update `status` / `comments`.
- `decided_by` and `decided_at` are filled automatically when a request is approved or rejected.

`public.payroll`

- One payroll row per user.
- Employees can read only their own payroll.
- Admins can create, update, and delete payroll rows.
- `net_salary` is generated by Postgres as `base_salary - deductions`, so client code cannot accidentally store inconsistent payroll totals.

## Frontend query contract

The agreed queries still work:

```ts
supabase.from('users').select('*').eq('id', userId);
supabase.from('users').update({ phone, address, profile_pic }).eq('id', userId);

supabase.from('attendance').insert({ user_id, date, check_in_time, status: 'present' });
supabase.from('attendance').update({ check_out_time }).eq('id', attendanceId);
supabase.from('attendance').select('*').eq('user_id', userId);
supabase.from('attendance').select('*, users(name)');

supabase.from('leave_requests').insert({
  user_id,
  type,
  start_date,
  end_date,
  remarks,
  status: 'pending',
});
supabase.from('leave_requests').select('*').eq('user_id', userId);
supabase.from('leave_requests').select('*, users(name)');
supabase.from('leave_requests').update({ status, comments }).eq('id', leaveId);

supabase.from('payroll').select('*').eq('user_id', userId);
supabase.from('payroll').update({ base_salary, deductions }).eq('user_id', userId);
```

RLS decides whether each query succeeds. The admin list queries are intentionally the same query shape as employee queries; admins see all rows, employees see only their own.

## Security notes for evaluation

- Passwords stay in Supabase Auth, never in `public.users`.
- `public.users.id` references `auth.users.id` with cascade delete.
- Role checks use `public.is_admin()`, a `security definer` function, to avoid recursive RLS policy problems.
- RLS is enabled on every application table.
- Guard triggers enforce column-level behavior that RLS alone cannot express cleanly.
- Date range and salary constraints reject invalid data at the database boundary.
- Indexes are included for the common dashboard queries: attendance by user/date, leave requests by user/status, and role checks.
